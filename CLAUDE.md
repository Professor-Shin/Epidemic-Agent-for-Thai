# Thai-context GABM-SEIR

LLM agents make daily behavioural choices inside an SEIR model of a synthetic Thai province.
The research question is whether **Thai-tuned** open-weight models behave differently from their
untuned base models, so the panel is a 2×2 of *model family × localisation*.

## Conditions

| | What decides behaviour | Run id prefix |
|---|---|---|
| A | nothing (pure SEIR) | `A_none_s0_*` |
| B | rule-based response to reported cases (`policy.alpha`) | `B_none_s0_*` |
| C | LLM residents, 40 agents × 4 actions | `C_<model>_s<seed>_*` |
| D | C plus a weekly LLM leader that sets the policy level | `D_<model>_s<seed>_*` |

Panel: `llama8b` / `typhoon8b` (Llama 3.1 8B base / Thai-tuned) and `qwen7b` / `openthaigpt7b`
(Qwen 2.5 7B base / Thai-tuned) form the 2×2. `seallm7b` is the SEA-multilingual control,
`mistral7b` the negative control, `qwen1_5b` a debug model excluded from any comparison.

## Invariants — breaking these silently corrupts the results

1. **Run ids must match across Colab and the server.** `make_run_id(condition, model_key, seed, settings)`
   hashes the effective config. `scripts/run_server.py` therefore makes the *same* `run_simulation`
   calls as notebooks 04/05. Change one side and finished work stops being recognised: runs are
   re-executed instead of skipped, and old and new results stop being comparable.
2. **`config/base.yaml` is the only place numbers live.** Never hardcode a parameter in a notebook.
   Every value also has a row in `data/parameter_sources.csv` with its source and a status of
   `data` | `literature` | `assumption`.
3. **`DAYS = 180` in notebooks 04/05**, while `base.yaml` keeps `days: 30` as the pilot. The horizon is
   part of the run id, so 30- and 180-day runs coexist safely. Analysis cells filter `days == DAYS`.
4. **Analysis filters `tag == ""`.** Smoke tests, sensitivity sweeps and action-order checks carry a tag
   and are excluded from the headline comparison. `outputs/metrics.csv` is a raw dump of *every* run
   including tagged ones — do not read a row count there as the number of experimental runs.
5. **Condition D is gated on C.** D runs only if C finished on all three seeds with `fallback_rate < 5%`.
   The gate lives in both `scripts/run_server.py:d_gate` and notebook 05 and must stay identical.
6. **`outputs/` is gitignored.** Results are never committed; they live on Colab Drive or the server and
   are pulled down with `rsync`. Any claim in a report must be traceable to a run id that still exists.

## Layout

- `gabm/` — the library: `sim.py` (day loop), `seir.py`, `agents.py`, `llm.py` (backends), `policy.py`,
  `contacts.py`, `sensitivity.py`, `io.py` (run folders, checkpoints), `analysis.py` (`load_runs`, metrics)
- `notebooks/00`–`05` — the Colab path, run in order
- `scripts/run_server.py` — headless equivalent of notebooks 02/04/05 for SLURM
- `scripts/server/` — SLURM toolkit; `server.env` holds every setting
- `config/base.yaml` — all parameters; `config/personas.csv` generated by notebook 00
- `report/` — Thai progress reports and the presentation

## Per-run folder (`outputs/runs/<run_id>/`)

`daily.csv` one row per simulated day · `decisions.jsonl` one record per agent per day ·
`leader.jsonl` (condition D) · `state.json` checkpoint after each day · `config.json` ·
`runtime.json` written only when the run finishes — `load_runs` skips folders without it,
so a missing `runtime.json` means the run was cut short.

## CU-AIM server

`ssh cuaim` → `/data/project/naruemon/siwakorn-s_gabm/Epidemic-Agent-for-Thai`

glibc is 2.17, below what current torch wheels need, so jobs run inside a Singularity container
(`ENV_KIND="container"`). Jobs read `scripts/server/server.env`; nothing is passed on the command line.

QoS wall-clock caps — **`TIME_GPU` above the cap leaves the job pending forever** in
`QOSMaxWallDurationPerJobLimit`, which looks like an ordinary queue wait but never runs:

| QoS | GPU | CPU / RAM | MaxWall |
|---|---|---|---|
| `gpu40g` | 1× A100-40GB | 16 / 64 GB | 8 h |
| `gpu40g64` | 1× A100-40GB | 64 / 128 GB | 12 h |
| `gpu10gh` | 2g.10gb slice | 16 / 64 GB | 4 days |
| `cpu40h` | — | 40 / 1 TB | 4 days |

Measured on an A100: ~3.5–4.3 s per simulated day, 51 min – 1 h 18 min per model for C + D at 180 days.
Every run checkpoints daily, so a timeout only needs `submit_all.sh` again — finished runs are skipped.

## Commands

```bash
# server (from the login node)
bash scripts/server/submit_all.sh smoke     # 2-day run of the first model, validates the whole path
bash scripts/server/submit_all.sh           # full panel: one GPU job per model, then the analysis job
squeue -u $USER

# pull results down
rsync -az cuaim:/data/project/naruemon/siwakorn-s_gabm/Epidemic-Agent-for-Thai/outputs/ ./outputs/
```

## Conventions

- Thai for conversation and for anything in `report/`; English for code, comments and commit messages.
- Prefer editing `server.env` over passing SLURM flags by hand, so every job is reproducible from the repo.
- When a result looks wrong, check the run id and `runtime.json` before suspecting the model.
